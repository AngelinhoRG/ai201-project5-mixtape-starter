# Mixtape — Codebase Map & Bug Fixes

## AI usage

I used Claude as as a code explainer after finding things myself and as a helper when I struggled to find things for myself. This is an honest account of a workflow where AI did most of the file reading and tracing, with verification and decision points built in along the way rather than only at the end.

**What it helped with:**
- **Initial codebase orientation.** Asked it to read the README and every file in `services/`, `routes/`, and `models.py`, then explain the app's structure and trace two call chains (rating a song, viewing a playlist). This produced the codebase map and the "patterns noticed" section — mechanical summarization I verified by spot-checking that the described relationships (e.g., `playlist_entries` carrying `position`/`added_by` columns) actually exist in `models.py`.
- **Forming initial hypotheses from a single read-through.** For all five tracked issues, it read the relevant service file once and proposed a specific root cause per bug (the Sunday `weekday()` check, the 24-hour feed threshold, the `songs[:-1]` slice, the missing `create_notification()` call, and a join-without-`.distinct()` for search). Four of these five held up under actual reproduction. One did not — see below.
- **Comparing structurally similar functions.** For issue #4, rather than guessing where a notification call should go, I had it read `add_to_playlist()` and `rate_song()` side by side and describe the structural difference between them. That comparison — "both look up song → look up actor → do side effect, but only one has the trailing `create_notification()` call" — was more reliable than reading `rate_song()` in isolation and speculating about what was "supposed" to happen.
- **Writing and running reproduction scripts.** For each bug, it wrote a standalone script that seeds real data and hits the actual Flask routes (not just calling the service function in isolation), then ran it and reported the actual output. Every claim of "reproduced" or "fixed" in the RCA entries is backed by an executed script's output, not an assertion about what the code "should" do.
- **Boundary-condition sweeps.** After each fix, it ran things I wouldn't have thought to check from reading the diff alone: all seven day-of-week transitions for the streak fix (not just Sat→Sun), a single-song playlist for the slice fix (would `[:-1]` on a 1-element list have hidden the only song?), and self-rating/re-rating edge cases for the notification fix.

**Where the AI's read-only diagnosis was wrong, and what caught it:**
- **Issue #3 (duplicate search results).** On first read, the code looked exactly like the classic bug the issue describes: `search_songs()` joins `Song` to `song_tags` without `.distinct()`, so a 3-tagged song should produce 3 duplicate rows. This diagnosis matched the code's shape, the issue report, and even the pre-written test's comment ("bug causes it to be 3") — it was stated with confidence before anything had actually been run. Per the reproduce-before-fixing rule, I had it write and run an actual reproduction script anyway, and the duplication didn't happen: `tests/test_search.py` passed all 5 tests, and a follow-up query using `.with_entities()` showed the join *does* produce 3 rows at the raw-SQL level, but SQLAlchemy's ORM automatically de-duplicates full-entity `.all()` results by primary key before they ever reach `.to_dict()`. The read-only diagnosis was plausible and would have been wrong to "fix" — changing code with no reproducible symptom isn't a real fix. This is exactly the failure mode the assignment warns about (plausible but wrong), and it was only caught by insisting on execution rather than accepting the first explanation. Issue #4 was substituted in its place.
- **A bug found by accident, not by hypothesis.** While reproducing issue #5 by calling the real `POST /playlists/<id>/songs` route (instead of inserting into `playlist_entries` directly), the call crashed with an unrelated `IntegrityError`. Neither of us had hypothesized this in advance — it only surfaced because I insisted on exercising the actual HTTP endpoint rather than settling for a same-effect direct DB write, which is what the AI's first draft of that reproduction script did. That crash turned out to be a second, real, undocumented bug (`add_to_playlist()`'s ORM `.append()` can't populate the NOT-NULL `position` column), which is now flagged as an aside in the Issue #5 entry rather than silently worked around.
- **Small mechanical mistakes in generated scripts.** A couple of the reproduction scripts initially failed with `IntegrityError: NOT NULL constraint failed` for an unrelated reason — referencing a model's `.id` before the object had been flushed to the DB (SQLAlchemy only assigns the UUID default at flush time, not at construction). This wasn't a diagnosis error, just a scripting bug, but it's another example of trusting execution output over assuming a first draft was correct.

## Main files and responsibilities

- **`app.py`** — Flask application factory (`create_app`). Owns the single `db = SQLAlchemy()` instance, reads `DATABASE_URL`/`SECRET_KEY` from the environment, registers the four blueprints (`songs`, `playlists`, `users`, `feed`) each under its own URL prefix, and calls `db.create_all()` on startup. There is no `if __name__ == "__main__": app.run()` path used in dev — the app is launched via `flask run` against the `create_app` factory (running `python app.py` double-imports the app and breaks SQLAlchemy's mapper registration).

- **`models.py`** — All SQLAlchemy models, imported from the shared `db` in `app.py`:
  - `User` — has `listening_streak` (int) and `last_listened_at` (datetime) columns used directly by streak logic (no separate streak table). Self-referential `friends` many-to-many via the `friendships` association table, keyed by `(user_id, friend_id)`. Friendship is **not automatically symmetric** — the app relies on inserting both directions at write time (see `seed_data.py`'s `add_friendship` helper, which inserts `(u1,u2)` and `(u2,u1)`).
  - `Song` — owns `shared_by` (FK to `User`) and has a `tags` many-to-many relationship via the `song_tags` association table (loaded eagerly with `lazy="subquery"`, i.e. tags come back as a separate query, not a SQL join).
  - `ListeningEvent` — one row per "user listened to song" action; this is the source of truth for both the streak service and the friend feed.
  - `Rating` — one row per `(user_id, song_id)` pair, enforced by a `UniqueConstraint`; rating twice updates the same row instead of creating a new one.
  - `Playlist` — songs live in `playlist_entries`, a many-to-many association table that (unlike `song_tags`/`friendships`) carries extra columns: `position` (explicit ordering, not insertion order), `added_by`, `added_at`.
  - `Notification` — flat table of `(user_id, notification_type, body, read)`; no polymorphic target, the `body` string is pre-rendered human-readable text at creation time.

- **`routes/`** — one blueprint per resource area (`songs.py`, `playlists.py`, `users.py`, `feed.py`). Every route does the same three things and nothing else: parse the request, call exactly one `services/` function, translate a `ValueError` into a 4xx JSON error. No business logic or DB queries appear in routes.

- **`services/`** — all business logic:
  - `streak_service.py` — `record_listening_event()` writes a `ListeningEvent` then calls `update_listening_streak()`, which compares calendar dates (`.date()`) of `now` vs `user.last_listened_at` to decide same-day/consecutive-day/gap.
  - `feed_service.py` — `get_friends_listening_now()` looks up `user.friends`, queries `ListeningEvent` for those friend IDs within a `RECENT_THRESHOLD` window, and dedupes to one (most recent) event per friend. `get_activity_feed()` is the same query without the recency filter, just a `LIMIT`.
  - `search_service.py` — `search_songs()` does an `ilike` match on title/artist.
  - `notification_service.py` — `create_notification()` is the single low-level writer; `add_to_playlist()` and `rate_song()` are the two call sites that are supposed to invoke it after their respective side effects.
  - `playlist_service.py` — `get_playlist_songs()` joins `playlist_entries` to `Song` and orders by `position`.

- **`tests/`** — one file per feature area (`test_streaks.py`, `test_search.py`, `test_playlists.py`), each spinning up an isolated in-memory SQLite DB per test via the `app`/fixture pattern. These tests directly encode the expected behavior for 3 of the 5 tracked issues (see below).

- **`seed_data.py`** — populates a dev DB with users, friendships, tagged songs, listening events (both "recent" and "older" — deliberately shaped to expose the feed bug), playlists, and one example notification.

## Data flow — rating a song (Issue #4's path)

`POST /songs/<song_id>/rate` → `routes/songs.py:rate()` parses `user_id`/`score` from the JSON body → calls `notification_service.rate_song(user_id, song_id, score)` → which validates the score range, looks up the `Song` and rater `User`, upserts a `Rating` row (update if `(user_id, song_id)` already exists, thanks to the `UniqueConstraint`), commits, and returns the `Rating`.

Compare with the sibling flow, `POST /playlists/<id>/songs` → `routes/playlists.py:add_song()` → `notification_service.add_to_playlist()`, which does its side effect (append song to playlist) **and then calls `create_notification()`** for the song's original sharer if the adder isn't the sharer themselves.

`rate_song()` has no equivalent call — it does the side effect (saves the `Rating`) but never calls `create_notification()`. That's the entire bug behind issue #4: the two functions are structural siblings (same shape: look up song → look up actor → do side effect → notify original sharer) and one of them is just missing its last step.

## Patterns noticed

- **Routes are thin, services own logic.** No route file touches `db.session` directly; they only call into `services/`. This makes each bug traceable to exactly one service function per the README's issue table.
- **Association tables are the model for "relationship + extra data."** Plain many-to-many (`friendships`, `song_tags`) uses a bare join table; the moment ordering/attribution matters (`playlist_entries`), the join table grows extra columns instead of becoming its own model. `Rating` is the outlier — it's a real model (not a join table) because it needs an identity and a score, but it still functions like a join row on `(user_id, song_id)`.
- **Sibling functions with the same shape diverge silently.** `add_to_playlist()` and `rate_song()` in `notification_service.py` are structurally parallel but only one performs the notification step — this is exactly the shape of Issue #4, and worth checking for elsewhere (e.g. any other "user did X to another user's song" action that should notify).
- **Time-based filtering is a recurring soft spot.** Both the streak logic (calendar-day math with a day-of-week special case) and the feed logic (a recency threshold) hinge on datetime arithmetic that's easy to get subtly wrong without a test walking through boundary days/hours — and indeed both are tracked issues (#1, #2).
- **Tests exist for 3 of the 5 issues on paper** (`test_streaks.py` → #1, `test_search.py` → #3, `test_playlists.py` → #5), with assertions and comments that describe the intended buggy behavior directly (e.g. `assert len(songs) == 5  # Bug causes this to return 4`). Running the suite shows only #1 and #5 actually fail — the #3 duplicate-search test passes, meaning that particular test's premise doesn't hold against the installed SQLAlchemy version (details below). Issues #2 and #4 have no existing test coverage and were reproduced manually.

## Root cause analysis (bugs chosen to fix)

### Issue #1 — Streak resets on Sunday
- **How I reproduced it:** Before touching any code, ran `tests/test_streaks.py::test_streak_increments_on_sunday` (failed: `assert 1 == 2`). Independently reproduced at the service-function level with a script that sets `user.listening_streak = 12`, `user.last_listened_at = <Saturday 2024-06-15 21:00 UTC>` (mirroring kenji's report of a 12-day streak through Saturday night), then calls `update_listening_streak(user, <Sunday 2024-06-16 09:00 UTC>)`. Result: streak became `1`, not `13`. As a control, I ran the identical one-day-gap transition landing on a Monday instead (Sunday night → Monday morning) and it correctly produced `13`, isolating that the day-of-week — specifically Sunday — was what triggered the bug, not just "one day passed." I used the service function directly rather than the live `POST /songs/<id>/listen` route because that route always uses `datetime.now()`, so hitting this through HTTP would require literally running the app on a real Sunday.
- **How I found the root cause:** Started at `routes/songs.py:listen()`, which just calls `streak_service.record_listening_event(user_id, song_id)`. That function creates the `ListeningEvent` and then delegates all streak math to `update_listening_streak(user, now)` — the only place streak logic lives. Reading that function's own docstring: *"If the user listened yesterday: streak increments by 1."* No day-of-week exception is documented anywhere in the file, the docstring, or the module header comment ("A streak increments when a user listens on consecutive calendar days"). Scanning the function body line by line against that spec, line 73 stood out immediately: `elif days_since_last == 1 and today.weekday() != 6:` has an extra clause with no corresponding mention in the spec. That mismatch between documented contract and implementation — not just "this looks suspicious" — is what confirmed this was the exact line, before making any change.
- **The root cause:** Python's `datetime.weekday()` returns `0` for Monday through `6` for Sunday. The condition `days_since_last == 1 and today.weekday() != 6` only takes the "increment" branch when exactly one day has passed *and* today is not a Sunday. When a consecutive-day listen happens to land on a Sunday, `today.weekday() != 6` evaluates to `False`, so the `elif` fails and execution falls through to `else: user.listening_streak = 1`, resetting the streak even though the user listened on consecutive calendar days exactly as the docstring says they should be credited for.
- **My fix and side-effect check:** Removed the `and today.weekday() != 6` clause, leaving `elif days_since_last == 1:` — the smallest possible change, touching only the one condition. To check for regressions: ran the full test suite (`pytest tests/`) — all 6 streak tests now pass, and the 2 pre-existing playlist failures (unrelated, not yet fixed) are untouched. Then swept all 7 consecutive-day transitions across a full week (Mon→Tue through Sun→Mon) with a script — every transition now correctly increments the streak by 1, including the previously-broken Sat→Sun. Also re-verified the three other branches of the same function are unaffected: same-day re-listen still makes no change, a 2-day gap still resets to 1, and a brand-new user with no history still starts at 1. Finally re-ran kenji's exact reported numbers (streak 12 on Saturday night → listen Sunday morning) and confirmed it now correctly produces 13.

### Issue #4 — No notification when a song is rated
- **How I reproduced it:** Before touching any code, hit the real routes via Flask's test client, following aaliya's exact two-step report. Seeded two songs shared by `aaliya`; created a `song_added_to_playlist` notification as a positive control confirming the notification pipeline itself works (count=1). Then called `POST /songs/<song_rated_id>/rate` as `kenji` with `{"user_id": kenji_id, "score": 5}` — got back `201` and a valid `Rating` dict (the score does save, matching aaliya's report that "the rating shows on the song"). Re-fetched `GET /users/<aaliya_id>/notifications` afterward: count stayed at `1`, no `song_rated`-type entry appeared — confirming the exact symptom (rating saves, no notification is created).
- **How I found the root cause:** Started at `routes/songs.py:rate()`, which calls `notification_service.rate_song(user_id, song_id, score)`. Read that function top to bottom: validate score → look up song → look up rater → upsert the `Rating` row → `db.session.commit()` → `return rating`. Nothing in that path calls `create_notification`. To confirm this was really the gap and not, say, a filtering bug in `get_notifications()`, I read `add_to_playlist()` in the same file, since it's the one flow the report says *does* work. Its shape is: look up song → look up actor → look up target (playlist) → do the side effect → `if song.shared_by != added_by_user_id: create_notification(...)`. `rate_song()` has the identical shape (look up song → look up actor → do the side effect) but stops right before that last conditional block — it's simply truncated one step short of its sibling. That structural side-by-side comparison, not just "the file with 'notification' in the name," is what confirmed the missing call was the entire bug, with no other logic to change.
- **The root cause:** `rate_song()` performs its side effect (creates or updates the `Rating` row and commits it) but never calls `create_notification()` for the song's original sharer. There is no conditional, no filter, no exception being silently swallowed — the function simply never contains the call that its sibling `add_to_playlist()` has. Ratings work, and notifications work (proven by the playlist-add path), but the one function that should connect them never does.
- **My fix and side-effect check:** Added a `create_notification()` call after the existing `db.session.commit()` in `rate_song()`, guarded by `if song.shared_by != user_id` (mirroring `add_to_playlist()`'s `if song.shared_by != added_by_user_id` guard, so a user rating their own shared song doesn't notify themselves), with `notification_type="song_rated"` and a body message following the same "`{actor} <verbed> your song '{title}'...`" phrasing as the playlist-add message. This is the smallest change that closes the gap — no other function needed to change since `create_notification()` already existed and worked. Re-ran the full test suite (`pytest tests/`): still 11 passed / 2 failed, the 2 failures being the pre-existing, not-yet-fixed playlist bug — no new failures. Re-ran the reproduction script: notification count now correctly goes from 1 → 2 with a `song_rated` entry. Checked two edge cases not explicitly in the report: (1) a user rating their *own* shared song correctly creates zero notifications (self-notify guard works); (2) a different user changing an existing rating (5 stars → 2 stars) fires a second notification with the updated score — this matches `add_to_playlist()`'s existing behavior of notifying on every call rather than only on the first, so the two sibling functions now stay consistent with each other.

### Issue #5 — Last playlist song never shows up
- **How I reproduced it:** Before touching any code, ran `tests/test_playlists.py::test_playlist_returns_all_songs` and `::test_playlist_returns_songs_in_order` (both failed — 5 seeded songs, only 4 returned). Then reproduced darius's exact two-step report via Flask's test client: seeded a playlist with 6 songs at positions 1–6, called `GET /playlists/<id>/songs` → got 5 songs back, missing `Track 6` (the newest). Inserted a 7th song at position 7 (mirroring simone adding a new song) and called `GET` again → `Track 6` was now present and `Track 7` was the new song missing — exactly matching "adding a new song frees the previously-missing song and hides the new one instead."
  - **Aside — found a second, unrelated bug while reproducing this:** calling the real `POST /playlists/<id>/songs` route (rather than inserting into `playlist_entries` directly) raises `sqlite3.IntegrityError: NOT NULL constraint failed: playlist_entries.position`. `add_to_playlist()` in `notification_service.py` does `playlist.songs.append(song)` through `Playlist.songs`, a plain `secondary=playlist_entries` relationship — that relationship has no way to populate the NOT-NULL `position`/`added_by` columns, so any call to the add-song endpoint crashes outright. This is not one of the 5 tracked issues and not part of my chosen three, but it's a real, live bug worth flagging — it may explain why manual QA of "add song" flows would misbehave in ways not captured by the current issue list.
- **How I found the root cause:** Started at `routes/playlists.py:get_songs()`, which calls `playlist_service.get_playlist_songs(playlist_id)`. Read that function top to bottom: it looks up the playlist, then queries `Song` joined to `playlist_entries` filtered by `playlist_id`, ordered ascending by `position` — this part is correct and matches the docstring ("Songs are returned in the order they were added"). The very last line, though, is `return [song.to_dict() for song in songs[:-1]]`. The function's own docstring note reads *"This function returns all songs in the playlist"* — directly contradicted by a slice that drops one. That contradiction between the documented contract and the last line of the function, combined with the query itself being demonstrably correct (confirmed by checking the ordering assertion separately), pinpointed the `[:-1]` slice as the sole cause rather than anything in the query/join logic.
- **The root cause:** the `songs` list returned by the query is already correctly sorted ascending by `position`, so the last element is always whichever song has the highest position — i.e., the most recently added song. `songs[:-1]` unconditionally drops that last element before building the response, regardless of playlist size, so the newest song is always excluded from the result.
- **My fix and side-effect check:** Changed `return [song.to_dict() for song in songs[:-1]]` to `return [song.to_dict() for song in songs]` — removing the slice entirely, since the query already returns exactly the set of songs that should be shown, in the right order. Ran the full test suite (`pytest tests/`): all 13 tests now pass, including `test_empty_playlist_returns_empty_list`, confirming the fix doesn't break the zero-songs case. Additionally checked a boundary case not covered by the existing tests: a playlist with exactly 1 song — under the old code, `[:-1]` on a single-element list silently returns `[]`, hiding the only song entirely; after the fix it correctly returns that one song. Re-ran darius's reported sequence end-to-end: a 6-song playlist now returns all 6, and adding a 7th correctly returns all 7 with no song hidden.

## Attempted but not reproduced: Issue #3 (duplicate search results)

- **Location examined:** `services/search_service.py:25-35`, `.outerjoin(song_tags, Song.id == song_tags.c.song_id)` without `.distinct()`.
- **Why I expected it to reproduce:** a raw SQL join between `Song` and `song_tags` for a 3-tagged song does produce 3 matching rows at the database level — confirmed directly by running the query with `.with_entities(Song.id, song_tags.c.tag_id)`, which returned 3 tuples for one song.
- **Why it doesn't actually reproduce:** despite that row-level fan-out, calling `.all()` on the same query when selecting full `Song` entities (not raw columns) returns only **1** `Song` object. The installed SQLAlchemy version (2.x ORM `Session.query()`) de-duplicates full-entity results by primary key automatically, collapsing the 3 joined rows back into a single `Song` before `.to_dict()` is ever called. Ran the full `tests/test_search.py` suite (including `test_search_no_duplicates_multi_tag_song`, whose comment claims "bug causes it to be 3") — all 5 tests pass in this environment.
- **Conclusion:** the code has the *shape* of the classic join-fan-out bug, and would genuinely duplicate rows in a context that doesn't auto-uniquify (e.g. a raw SQL query, or a different ORM/version), but as actually deployed here it does not reproduce. I did not implement a fix for it, and swapped in Issue #4 instead. Flagging this rather than "fixing" a test that already passes, since changing code with no reproducible symptom isn't a real fix — the join is arguably still worth simplifying for clarity/performance (fetching an unused join every search), but that's a cleanup, not a bug fix.

## Deferred: Issue #2 (Friends Listening Now shows stale entries)

- **Location:** `services/feed_service.py:13`, `RECENT_THRESHOLD = timedelta(hours=24)`.
- **Root cause:** a 24-hour recency window means a friend who listened at 11pm still shows up as "listening now" at 9am the next morning — a full calendar day later.
- **How I reproduced it:** manually, via direct service calls (no existing test coverage). Seeded a `ListeningEvent` for a friend timestamped ~10 hours in the past and confirmed `get_friends_listening_now()` still returned it; a control event at 30 hours in the past was correctly excluded, isolating that the threshold itself (not the query logic) is the problem. `seed_data.py`'s own comments (`"Older events (1-14 days ago) — should NOT appear in listening now after fix"`, starting at just 2 hours ago) confirm the intended threshold is much shorter than 24 hours — likely ~30 minutes, matching the "within the past 30 minutes" comment on the "recent" seed events.
- **Not fixed in this pass** — left open alongside #3 since only 3 fixes were required. Noted here because it shares the same root-cause *category* as #1 (imprecise datetime/calendar-boundary handling), so revisiting it later should go quickly using the same lens.
